值区顶部 key 信息区 · 20 套新视觉方案

每套方案渲染同一组真实信息：key 名 / 类型 / TTL / encoding / 大小 / 更多操作；每组给「string + TTL」与「hash + 永久」两个实例，并附深浅双主题。所有方案共用同一份 DOM，仅以 CSS 塑形，落地时可只替换 ticket-head 的样式块。

下面 00 为现有「票根 + 水印」基线，仅作对照；20 套新方案均刻意避开票根、穿孔、水印语言。

选型提示：顶部信息区高度有限、要扛住长 key 名与窄侧栏。建议重点看 03 / 08 / 16（信息可读性与密度）、04 / 13 / 19（轻量不抢戏）、07 / 20（氛围感但要看亮色主题的接受度）。

00

现状基线：票根 + 水印

左侧竖排类型票根 + 虚线穿孔 + 右下 64px 水印首字母；min-height 75px

对照
  • 优点有明确的「票据」隐喻，和值区内容区区分度高。
  • 代价竖排类型字可读性弱；水印在浅色主题几乎消失；高度偏高。
  • 问题信息只有两行，标题行与元信息行之间缺少视觉锚点，扫视时容易漏掉 TTL。
01

终端命令行

❯ key --ttl= --enc= --size=：把 header 写成一行 Redis 命令

开发味
  • 优点与产品气质（CLI 控制台）同源，长 key 名自然成为"命令"，不需要额外容器。
  • 优点元信息变成 flag，弱化标签感；cli-bg 底色与值区正文区分清楚。
  • 代价flag 写法对非技术用户有门槛；闪烁光标需尊重 reduced-motion。
02

状态栏色块

vim statusline：类型块反白、名字块 elevated、元信息贴边分格

沉浸感
  • 优点类型色块是最强的类型识别信号，纵向高度仅 42px，省出值区空间。
  • 优点整条 bar 无内边距断点，贴着值区顶边，像编辑器状态栏一样安静。
  • 代价满宽色块对亮色主题要求高，颜色透明度需按主题单独调。
03

规格表

名字一行 + 三列均分、竖向分隔的 label / value 规格区

信息最稳
  • 优点label 恒在 value 正上方，TTL 与 encoding 不再靠分隔符区分，扫读成本最低。
  • 优点三列均分天然适配 Memcached 的 TTL / 大小 / flags 三项。
  • 代价头部约 90px，比现状还高；窄侧栏下三列会挤，需在 240px 以下降级为两列。
04

芯片流

类型实底 chip + 三项描边 chip，右对齐成一条可换行的胶囊行

轻量
  • 优点胶囊与项目现有按钮语言一致；类型色只出现在一枚 chip 上，克制。
  • 优点chip 可换行：窄侧栏下自动落第二行，不会把 key 名压没。
  • 代价chip 的内边距让三项元信息占宽明显，长 key 名可用宽度变少。
05

类型色脊

左缘 3px 类型色竖脊 + 同色 9% 渐变底，其余保持现状排版

最小改动
  • 优点只加一条脊和一个渐变，就能去掉「票根」的装饰性，保留全部现有排版。
  • 优点类型色在余光里可辨，切换 key 时不需要读类型文字。
  • 代价三种元信息仍是单行以分隔符区分，信息层级没有变化。
06

文件夹页签

名字坐在一枚凸起的页签上，元信息留在下方横轨

实体感
  • 优点页签与下方值区形成「文件—内容」的空间关系，比票根更直白。
  • 优点页签宽度随名字收缩，长名字时仍用 ellipsis，不会被撑开。
  • 代价顶部需要 8px 空隙容纳页签，整体高度略高；多标签场景会与底部页签语言重复。
07

悬浮玻璃

内缩 8px 的圆角毛玻璃条 + backdrop-filter: blur(10px)

氛围
  • 优点信息条像浮在值区之上，层次感强，深色主题下质感尤其好。
  • 优点内缩后与值区左右留白同宽，视觉上更像一个独立浮层。
  • 代价blur 对低端 GPU 有开销；亮色主题下玻璃感较弱，已单独降阴影补救。
08

倒计时焦点

TTL 放大到 20px 独立右置，encoding / 大小降为两列小注

重点突出
  • 优点TTL 是排查缓存问题时最常看的一项，放大后无需眯眼；永久 key 显示 ∞ 同样醒目。
  • 优点类型色点 + 小写类型名，低干扰地保留类型信息。
  • 代价高亮 TTL 会让 encoding 显得次要，仍需保留小标签避免歧义。
09

TTL 环

34px 环形进度（类型色弧 + 中心剩余时长），像一块小仪表

图形化
  • 优点环形把「剩余比例」变成可感的图形；中心文字解决精确值。
  • 优点类型色弧同时承担类型识别，一元素两用。
  • 代价需要知道 key 的 TTL 上限才能算比例（可用 24h / 7d 归一，语义要提前定）；永久 key 环为空。
10

索引卡

横线纸底 + 左侧红色竖线，元信息像卡片上的三个字段

纸质
  • 优点横线纸让两行内容有落点，长 key 名像写在卡片上；与值区的纯色面形成材质差。
  • 优点深色主题下横线极淡，不会变成"作文本"。
  • 代价装饰性较强，与「简洁暗色工具」的整体气质有冲突风险；内缩后高度增加。
11

报头

类型作 eyebrow 小字 + 18px 名字 + 双线底，元信息贴右下

编辑感
  • 优点「报头」天然强调标题层级，名字变大后长 key 的可读性反而提升（截断更直观）。
  • 优点双线底与值区内容形成明显的版面分界。
  • 代价名字变大导致可见字符变少；右下角元信息与右上 ⋮ 容易挤，需要留出按钮位。
12

头像头部

32px 圆形类型字母 + 两行布局（名字 / 点分元信息）

亲和
  • 优点两行结构把三项元信息压成一行点分小字，宽度占用最小，适合窄侧栏。
  • 优点圆形类型字母与连接列表的引擎图形语言呼应。
  • 代价去掉 label 后需要用户记住数值顺序（TTL / 编码 / 大小）；字母缩写需与类型一致。
13

代码注解

key: name @ttl(3600s) @enc(raw) @size(2.4KB)，左缘类型色竖条

极客
  • 优点注解语法与「代码工具」语境一致，TTL 等值按类型色着色，扫读快。
  • 优点全等宽排版让长 key 与值区正文共享节奏，切换不跳。
  • 代价注解括号增加了字符噪音；非技术用户可能读成命令而不是元信息。
14

印章

右侧 42px 旋转 -9° 的双环印章，以类型首字母落款

个性
  • 优点印章足够克制又有个性，类型色 + 双环让它在两种主题下都成立。
  • 优点与现有票根隐喻同源但形式不同（落款 vs 票根），过渡自然。
  • 代价旋转元素需要给 ⋮ 让位（右侧多留 52px）；单个字母信息量低，仍需其他位置给类型文字。
15

键帽

key 名装进 3D 键帽（底边 2px 实影），类型为小色标

实体
  • 优点「key」的双关被具象化成键帽，产品记忆点强。
  • 优点键帽天然限宽，长名字截断看起来是设定而不是缺陷。
  • 代价键帽边框+底影与项目「轻边框」风格有偏差；名字越长键帽越宽，极端情况会挤占元信息。
16

台账

三列 label ····· value 点线引导，像账本的字段行

窄栏友好
  • 优点点线把 label 与 value 绑定，三列在窄栏下依然可读；等宽数字对齐。
  • 优点无额外装饰色，主题切换零负担。
  • 代价点线在缩放 125% 下可能显脏，需要按 1px dotted 固定；比芯片方案更"表格化"。
17

类型渐变

左起 13% 类型色渐变铺底 + 2px 渐变下划线

氛围
  • 优点不增加任何结构，只借渐变表达类型；与值区之间有一条彩色分界。
  • 优点类型色同时点亮 size 值，视觉上「类型 → 大小」形成呼应。
  • 代价渐变对深色主题友好，亮色主题需压到 10% 以下，否则显脏。
18

刻度尺

名字行下方 6px 刻度带，类型色填充段表示大小占比

图形化
  • 优点让「大小」从数字变成比例，评估大 key 时一眼有数。
  • 优点刻度线轻，不抢 key 名。
  • 代价需要定义「满分」基准（如 10 万字符），语义要写清楚；否则容易误读。
19

极简细线

string/ key · 3600s · raw · 2.4KB，仅保留一条底线

最安静
  • 优点信息全部压成一行，头高最低，把纵向空间还给值区。
  • 优点与值的代码正文共享等宽节奏，像编辑器面包屑。
  • 代价去掉 label 后需约定值顺序；类型/元信息全是低对比灰，弱视用户不友好。
20

霓虹顶边

顶缘 2px 类型色发光边 + 同色 12% 底，其余保持现状排版

氛围张力
  • 优点一条发光边就能区分类型与「当前值区」，不占用布局空间。
  • 优点名字带极淡光晕，和深色主题的「深海 / 森林」皮肤很搭。
  • 代价发光强度稍高就有霓虹感；亮色主题需要独降光晕（已单独处理）。
